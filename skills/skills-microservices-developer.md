# Skill: Microservices Developer

## Purpose

Generate production-ready microservice implementation code from **Spec Kit artifacts** (spec.md, plan.md, tasks.md) created by the Microservices Designer skill. The Developer Skill dynamically discovers and enforces enterprise coding standards from the **shopizer-context-studio MCP server**. Supports multiple technology stacks (Spring Boot, Python FastAPI, Node.js Express, Quarkus) and generates complete deployment artifacts for Kubernetes/OpenShift.

## Architecture

### NEW: Spec Kit-Driven Development

```
spec.md (WHAT to build)
    ↓
plan.md (HOW to build)
    ↓
tasks.md (WHEN to build)
    ↓
Enterprise Standards (shopizer-context-studio MCP)
    ↓
Developer Skill
    ↓
Production-Ready Code
```

**Key Principle**: Spec Kit artifacts are the **authoritative source** for implementation. OpenAPI and SQL schemas are **supporting artifacts** that must align with the Spec Kit.

## Inputs

### Required Inputs

1. **Spec Kit Specification**: `output/specs/{service}/spec.md`
   - Complete functional specification (language-agnostic)
   - Functional requirements, commands, queries, events
   - Business rules and domain model
   - Generated by Microservices Designer skill
   - **This is the authoritative source for WHAT to build**

2. **Spec Kit Technical Plan**: `output/specs/{service}/plan.md`
   - Implementation plan with architecture, tech stack, component structure
   - Data model design, API design, event design
   - Security, caching, observability, testing, deployment strategy
   - Generated by Microservices Designer skill
   - **This is the authoritative source for HOW to build**

3. **Spec Kit Task Breakdown**: `output/specs/{service}/tasks.md`
   - Task breakdown with phases, sprints, story points
   - Task dependencies and sequencing
   - Generated by Microservices Designer skill
   - **This is the authoritative source for WHEN to build (task order)**

4. **OpenAPI Specification**: `output/swagger/{service}-openapi.yaml`
   - Complete API specification with endpoints, schemas, security
   - Generated by Microservices Designer skill from Spec Kit
   - **Supporting artifact - must align with spec.md and plan.md**

5. **Database Schema**: `output/sql/{service}-schema.sql`
   - DDL for service-owned tables
   - Generated by Microservices Designer skill from Spec Kit
   - **Supporting artifact - must align with spec.md and plan.md**

6. **Technology Stack**: One of:
   - `springboot` - Spring Boot 3.x with Java 17
   - `python` - Python 3.11+ with FastAPI
   - `nodejs` - Node.js 20+ with Express and TypeScript
   - `quarkus` - Quarkus 3.x with Java 17

7. **Deployment Target**: One of:
   - `kubernetes` - Standard Kubernetes deployment
   - `openshift` - OpenShift with Routes
   - `docker` - Docker Compose only

8. **shopizer-context-studio MCP Server**: 
   - Authoritative source for enterprise implementation standards
   - Dynamically discovered coding standards, naming conventions, architecture constraints
   - Security requirements, testing requirements, deployment standards

### Optional Inputs

9. **Design Documentation**: `output/design/{service}-design.md`
   - Comprehensive design documentation
   - Used for additional context and documentation

## Enterprise Standards Discovery

### MinIO Storage Integration

The Developer Skill **must retrieve** enterprise standards from MinIO object storage before generating any code.

**MinIO is the authoritative source** for implementation standards and organizational guidelines.

### Standards Retrieval Process

1. **List MinIO buckets** to find the "coding-standards" bucket
2. **Download standards documents** from the "coding-standards" bucket
3. **Parse and apply** standards during code generation

**Fixed Bucket Name:**
- Bucket: `coding-standards` (fixed name, not application-specific)
- Contains all organizational coding standards, architecture guidelines, security policies, etc.

### Standards to Discover

The Developer Skill must dynamically discover and load from MinIO:

- **Coding Standards**: Language-specific best practices, naming conventions
- **Package Structures**: Folder structures, layering conventions
- **Logging Standards**: Structured logging, log levels, correlation IDs
- **Error Handling Standards**: Exception hierarchies, error codes, error messages
- **Security Standards**: Authentication, authorization, encryption, input validation
- **Testing Standards**: Test coverage, test patterns, test data management
- **Observability Standards**: Metrics, tracing, health checks
- **Deployment Standards**: Container configuration, resource limits, scaling policies
- **Integration Standards**: API contracts, event schemas, circuit breakers
- **Technology-Specific Guidance**: Framework-specific implementation patterns

### Discovery Rules

1. **No Assumptions**: The Developer Skill must NOT assume any document names, storage locations, or repository structures
2. **MinIO Determines Standards**: MinIO storage determines what standards apply
3. **Mandatory Compliance**: Enterprise standards override default code generation behavior
4. **Dynamic Loading**: Standards are loaded at runtime from MinIO, not hardcoded
5. **Fallback**: If MinIO standards not found, use local `context/` directory or defaults

### MinIO Output Publishing

After code generation is complete, the Developer Skill **must upload** the generated `README.md`
to the **application bucket** (`shopizer`) in MinIO, under a virtual folder path using the
microservice name:

**Target path in MinIO:**
```
shopizer/output/{service-name}/README.md
```

**Examples:**
- `catalog-service` → `shopizer` bucket, object `output/catalog-service/README.md`
- `order-service`   → `shopizer` bucket, object `output/order-service/README.md`
- `inventory-service` → `shopizer` bucket, object `output/inventory-service/README.md`

The `shopizer` bucket is the fixed application bucket and is always assumed to exist.
No separate bucket creation is required.

### Step 0.5: Load Enterprise Standards from MinIO

**Purpose**: Retrieve and load enterprise implementation standards from MinIO object storage

**Actions**:
1. List MinIO buckets to find standards/constitution bucket
2. Download enterprise standards documents
3. Parse coding standards, naming conventions, architecture constraints
4. Load security requirements, testing requirements, deployment standards
5. Store standards as mandatory implementation constraints

**MinIO Retrieval Process**:

```typescript
// Step 1: List buckets to find standards bucket
const buckets = await mcpTool('use_mcp_tool', {
  server_name: 'minio',
  tool_name: 'list_buckets',
  arguments: {}
});

// Step 2: Find the "coding-standards" bucket (fixed name)
const standardsBucket = buckets.find(b => b.name === 'coding-standards');

if (!standardsBucket) {
  console.warn('⚠️  Bucket "coding-standards" not found in MinIO, using defaults');
  return loadDefaultStandards();
}

console.log(`📦 Using coding standards bucket: coding-standards`);

// Step 3: List documents in standards bucket
const objects = await mcpTool('use_mcp_tool', {
  server_name: 'minio',
  tool_name: 'list_objects',
  arguments: {
    bucketName: standardsBucket.name,
    recursive: true
  }
});

// Step 4: Download all standards documents
for (const obj of objects) {
  await mcpTool('use_mcp_tool', {
    server_name: 'minio',
    tool_name: 'download_object',
    arguments: {
      bucketName: standardsBucket.name,
      objectName: obj.name,
      filePath: `temp/standards/${obj.name}`
    }
  });
}

// Step 5: Parse and load standards
const standards = {
  codingStandards: await parseStandards('temp/standards/coding-standards.md'),
  architectureGuidelines: await parseStandards('temp/standards/architecture.md'),
  securityRequirements: await parseStandards('temp/standards/security.md'),
  testingStandards: await parseStandards('temp/standards/testing.md'),
  deploymentStandards: await parseStandards('temp/standards/deployment.md')
};
```

**Standards to Retrieve**:
- Coding standards for chosen language (Java/Python/TypeScript)
- Package/module structure conventions
- Layering conventions (API → Application → Domain → Infrastructure)
- Naming conventions (classes, methods, variables, files)
- Logging standards (structured logging, log levels, correlation IDs)
- Error handling standards (exception hierarchies, error codes)
- Security standards (authentication, authorization, encryption)
- Testing standards (coverage targets, test patterns)
- Observability standards (metrics, tracing, health checks)
- Deployment standards (resource limits, scaling policies)
- Integration standards (API contracts, event schemas)

**Validation**:
- [ ] MinIO server is accessible
- [ ] Standards bucket exists
- [ ] Standards documents are downloaded successfully
- [ ] Standards are applicable to chosen technology stack
- [ ] Fallback to defaults if MinIO unavailable

**Failure Condition**: If MCP server is unavailable or standards cannot be loaded, **WARN** but continue with default standards.

**Output**: Enterprise standards stored as implementation constraints.

## Task-Driven Development

### Principle

The Developer Skill **must implement** the system in the order defined by **tasks.md**.

### Example Task Sequence

```
TASK-001: Generate Domain Model
    ↓
TASK-002: Generate Repository Layer
    ↓
TASK-003: Generate Service Layer
    ↓
TASK-004: Generate APIs
    ↓
TASK-005: Generate Event Publishers
    ↓
TASK-006: Implement Security
    ↓
TASK-007: Implement Observability
    ↓
TASK-008: Generate Tests
    ↓
TASK-009: Generate Deployment Assets
    ↓
TASK-010: Generate Documentation
```

### Task Dependencies

Implementation sequencing **must follow** task dependencies defined in tasks.md.

If TASK-003 depends on TASK-001 and TASK-002, then:
1. Complete TASK-001 first
2. Complete TASK-002 second
3. Complete TASK-003 third

### Task Traceability

Every generated artifact **must record**:
- **Task ID**: Which task generated this artifact (e.g., TASK-INV-003)
- **Requirement ID**: Which requirement this implements (e.g., FR-INV-001)
- **Specification Reference**: Which section of spec.md (e.g., spec.md Section 7.1)
- **Governance Source**: shopizer-context-studio MCP server

Example JavaDoc:
```java
/**
 * Inventory aggregate root.

 * @requirement FR-INV-001 - Create Inventory
```

## Implementation Precedence

### Precedence Order

When conflicts occur, resolve using this precedence:

1. **spec.md** - Authoritative for WHAT to build
2. **plan.md** - Authoritative for HOW to build
3. **tasks.md** - Authoritative for WHEN to build (task order)
4. **Enterprise standards from shopizer-context-studio** - Authoritative for implementation style and governance

```java
/**
 * Inventory aggregate root.
 * 
 * @specification spec.md Section 7.1 - Aggregate Roots
 * @requirement FR-INV-001 - Create Inventory
 * @task TASK-INV-003 - Generate Domain Model
 * @governance shopizer-context-studio MCP server
 */
@Entity
@Table(name = "inventory")
@Getter
@Setter
@NoArgsConstructor
public class Inventory {
    
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    @Column(nullable = false, unique = true)
    private String sku;
    
    @Column(nullable = false)
    private Integer quantity;
    
    @Column(nullable = false)
    private Integer reserved;
    
    @Column(nullable = false)
    private Boolean available;
    
    /**
     * Reserve inventory for an order.
     * 
     * @specification spec.md Section 4 - CMD-INV-003
     * @businessRule BR-INV-001 - Product availability check
     * @businessRule BR-INV-004 - Reservation expiry
     */
    public ReservationResult reserve(String orderId, Integer quantity) {
        // Business rule: BR-INV-001
        if (!canReserve(quantity)) {
            throw new InsufficientInventoryException(
                sku, getAvailableQuantity(), quantity
            );
        }
        
        Reservation reservation = new Reservation(
            UUID.randomUUID().toString(),
            orderId,
            quantity,
            LocalDateTime.now().plusMinutes(15) // BR-INV-004
        );
        
        this.reserved += quantity;
        this.reservations.add(reservation);
        
        return new ReservationResult(reservation.getId(), true);
    }
    
    private boolean canReserve(Integer quantity) {
        return available && getAvailableQuantity() >= quantity;
    }
    
    private Integer getAvailableQuantity() {
        return quantity - reserved;
    }
}
```

```python
"""
Inventory aggregate root.

Specification: spec.md Section 7.1 - Aggregate Roots
Requirement: FR-INV-001 - Create Inventory
Task: TASK-INV-003 - Generate Domain Model
Governance: shopizer-context-studio MCP server
"""
from dataclasses import dataclass, field
from datetime import datetime, timedelta
from typing import List, Optional
from uuid import uuid4

@dataclass
class Inventory:
    """Inventory aggregate root."""
    
    id: Optional[int] = None
    sku: str = ""
    quantity: int = 0
    reserved: int = 0
    available: bool = True
    reservations: List['Reservation'] = field(default_factory=list)
    
    @property
    def available_quantity(self) -> int:
        """Calculate available quantity (total - reserved)."""
        return self.quantity - self.reserved
    
    def can_reserve(self, quantity: int) -> bool:
        """Check if inventory can be reserved."""
        return self.available and self.available_quantity >= quantity
    
    def reserve(self, order_id: str, quantity: int, ttl_minutes: int = 15) -> str:
        """
        Reserve inventory for an order.
        
        Specification: spec.md Section 4 - CMD-INV-003
        Business Rule: BR-INV-001 - Product availability check
        Business Rule: BR-INV-004 - Reservation expiry
        """
        # BR-INV-001: Check availability
        if not self.can_reserve(quantity):
            raise InsufficientInventoryError(
                f"Product {self.sku} has insufficient inventory. "
                f"Available: {self.available_quantity}, Requested: {quantity}"
            )
        
        reservation_id = str(uuid4())
        expires_at = datetime.utcnow() + timedelta(minutes=ttl_minutes)  # BR-INV-004
        
        reservation = Reservation(
            id=reservation_id,
            order_id=order_id,
            quantity=quantity,
            expires_at=expires_at
        )
        
        self.reserved += quantity
        self.reservations.append(reservation)
        
        return reservation_id
```

```typescript
/**
 * Inventory aggregate root.
 * 
 * @specification spec.md Section 7.1 - Aggregate Roots
 * @requirement FR-INV-001 - Create Inventory
 * @task TASK-INV-003 - Generate Domain Model
 * @governance shopizer-context-studio MCP server
 */
export class Inventory {
  constructor(
    public id?: number,
    public sku: string = '',
    public quantity: number = 0,
    public reserved: number = 0,
    public available: boolean = true,
    public reservations: Reservation[] = []
  ) {}

  get availableQuantity(): number {
    return this.quantity - this.reserved;
  }

  canReserve(quantity: number): boolean {
    return this.available && this.availableQuantity >= quantity;
  }

  /**
   * Reserve inventory for an order.
   * 
   * @specification spec.md Section 4 - CMD-INV-003
   * @businessRule BR-INV-001 - Product availability check
   * @businessRule BR-INV-004 - Reservation expiry
   */
  reserve(orderId: string, quantity: number, ttlMinutes: number = 15): string {
    // BR-INV-001: Check availability
    if (!this.canReserve(quantity)) {
      throw new InsufficientInventoryError(
        `Product ${this.sku} has insufficient inventory. ` +
        `Available: ${this.availableQuantity}, Requested: ${quantity}`
      );
    }

    const reservationId = uuidv4();
    const expiresAt = new Date(Date.now() + ttlMinutes * 60 * 1000); // BR-INV-004

    const reservation: Reservation = {
      id: reservationId,
      orderId,
      quantity,
      expiresAt,
      status: 'ACTIVE'
    };

    this.reserved += quantity;
    this.reservations.push(reservation);

    return reservationId;
  }
}
```
