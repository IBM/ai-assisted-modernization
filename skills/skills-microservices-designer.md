# Skill: Microservices Designer

## Purpose
Generate detailed microservice design artifacts (OpenAPI, SQL schemas, design documents) from **existing Spec Kit artifacts** (spec.md, plan.md, tasks.md) that were created by the Architect Agent.

**IMPORTANT**: This skill does NOT generate Spec Kit artifacts. It consumes them to produce design artifacts.

**Input Sources:**
- Spec Kit artifacts from Architect Agent (spec.md, plan.md, tasks.md)
- Discovery documents from MinIO
- Source code
- SQL / DDL files
- Microservice identification CSV

## Inputs

### Required Inputs
- **Microservice Identification CSV**: Path to CSV file with service boundaries (e.g., `output/microservices-decomposition.csv`)
- **Source Code Directory**: Root directory containing application code
- **SQL/DDL Files**: Database schema files

### Optional Inputs
- **Bounded Context Specification**: Markdown file with context boundaries
- **Context Studio MCP Server**: MCP server name for enrichment (e.g., `context-studio`, `shopizer-context-studio`)
- **Context ID**: Context identifier for MCP queries

### Configuration
The skill accepts configuration via:
1. **Command-line parameters** (when executed as command)
2. **Prompt parameters** (when activated via prompt)
3. **Environment variables**
4. **Default discovery** (auto-detect from project structure)

**Example Configuration:**
```yaml
inputs:
  microservice_csv: "output/microservices-decomposition.csv"
  source_code: "."
  sql_files: "*.sql"
  bounded_context: "output/bounded-context-specification.md"
  
context_studio:
  enabled: true
  mcp_server: "context-studio"  # or "shopizer-context-studio", etc.
  context_id: "ctx_xxxxx"  # auto-detected or specified
  agent_persona: "MicroservicesArchitect"

spec_kit:
  enabled: true
  # IMPORTANT: Do NOT set mcp_server here. The spec-kit MCP server tools
  # (speckit_specify / speckit_plan / speckit_tasks) are broken — the underlying
  # specify CLI v0.9.4 does not expose those subcommands.
  # Use the Bob slash commands instead (see Step 3 below).
  slash_commands: true   # /speckit.specify, /speckit.plan, /speckit.tasks
  auto_generate_spec: true
  auto_generate_plan: true
  auto_generate_tasks: true
```

## Outputs
- `/output/swagger` - OpenAPI/Swagger specifications (derived from Spec Kit)
- `/output/sql` - SQL ownership and migration scripts (derived from Spec Kit)
- `/output/design` - Design markdown documents (references Spec Kit)

## Artifacts Generated
For each identified microservice, the Designer generates design artifacts FROM existing Spec Kit files:

**Input (from Architect Agent):**
1. `spec.md` - Functional requirements (already exists)
2. `plan.md` - Technical architecture (already exists)
3. `tasks.md` - Implementation sequence (already exists)

**Output (generated by Designer):**
1. **OpenAPI/Swagger specification** - Complete API definition (derived from spec.md + plan.md)
2. **SQL ownership and migration script** - Database schema and ownership (derived from spec.md + plan.md)
3. **Design markdown document** - Comprehensive design documentation (references Spec Kit artifacts)

## Mandatory NFRs (Non-Functional Requirements)
All generated microservices must include:
- **JWT Security** - Token-based authentication
- **Timeout = 10 seconds** - Request timeout configuration
- **Retry = 3 attempts** - Retry policy with exponential backoff
- **Correlation IDs** - Request tracing across services
- **Structured Logging** - JSON-formatted logs with context
- **Health Checks** - Liveness and readiness endpoints
- **Auditability** - Audit trail for all operations
- **Observability** - Metrics, traces, and logs
- **Saga / Outbox guidance** - Distributed consistency patterns

## Evidence Sources

### From Neo4j Knowledge Graph (Primary — queried first)
The Neo4j graph is queried **per service** immediately after MinIO retrieval, before
spec-kit artifacts are generated. It provides objective, code-derived facts that
cannot be obtained from discovery documents:

- **Method signatures + descriptions** → OpenAPI `operationId`, `summary`, request shapes
- **Class-level business rules** → OpenAPI error responses, SQL `CHECK` constraints, spec validation rules
- **BoundedContext recommendation score** → migration phase ordering in design doc
- **Cross-context DEPENDS_ON edges** → upstream/downstream integration sections

**Neo4j Queries run (once per service, see Step 2.5):**
- Query A: business rules on classes owned by this bounded context
- Query B: method signatures and descriptions for classes in this context
- Query C: bounded context recommendation score
- Query D: DEPENDS_ON edges crossing into or out of this context

### From MinIO Object Storage (Secondary)
Discovery documents are retrieved from MinIO storage:
- Business flows and execution patterns
- Business rules and validations (coarse-grained — graph rules take precedence)
- Database inventory and relationships
- Architecture patterns
- External integrations
- Module dependencies

**MinIO Retrieval Process:**
1. List buckets to find latest discovery bucket
2. Download all 7 discovery documents
3. Parse documents for evidence extraction

**Discovery Documents Retrieved:**
- **DISCOVERY_SUMMARY.md** - Application overview
- **ARCHITECTURE_INVENTORY.md** - Architecture documentation
- **BUSINESS_RULES.md** - Business rules inventory
- **INTEGRATIONS.md** - External integrations
- **DEPENDENCY_MAP.md** - Module dependencies
- **DATABASE_INVENTORY.md** - Database schema
- **DATABASE_SUMMARY.md** - Database analysis

### From Local Files
The skill also scans for and uses:
- **Source code**: All directories containing application code
- **SQL scripts**: All `.sql` files in project
- **Microservice identification**: CSV/markdown files with service definitions
- **Bounded context**: Markdown files with context specifications

### Fallback Mode
If MinIO is not available, the skill can work with:
- Local discovery documents in `context/` directory
- Direct file-based evidence (markdown files)
- Source code analysis
- SQL schema parsing
- CSV-only mode (minimal evidence)

If Neo4j is not available, skip Step 2.5 and proceed — graph evidence is enrichment,
not a hard dependency. Log a warning and continue with empty `graphEvidence` objects.

## Output Structure

Spec Kit artifacts live under `specs/` (created by the slash commands).
Design artifacts (OpenAPI, SQL, design docs) live under `output/`.

## Rules
1. **CSV is the source of truth** for service boundaries
2. **Spec Kit artifacts are the primary design source of truth** - OpenAPI specifications, SQL schemas, and design documents must be derived from spec.md, plan.md, and tasks.md
3. **Context Studio provides discovery evidence only** - Not direct design input
4. **Do not generate generic services** - All services must be specific and well-defined
5. **Do not create cross-microservice foreign keys** - Services own their data
6. **Capture unclear ownership as Open Questions** - Document ambiguities
7. **Include evidence traceability** in all generated artifacts
8. **Mark APIs as Existing or Proposed** - Distinguish between current and future state
9. **Generate complete artifact set per microservice** - Spec Kit artifacts first, then design artifacts

### Step 2: Gather Evidence from MinIO, Local Sources, and Neo4j
```typescript
const evidence = {
  minio: {},
  local: {}
};

// Retrieve discovery documents from MinIO
console.log(`🔍 Retrieving discovery documents from MinIO...`);

try {
  // Step 2.1: List all buckets
  const buckets = await mcpTool('use_mcp_tool', {
    server_name: 'minio',
    tool_name: 'list_buckets',
    arguments: {}
  });
  
  // Step 2.2: Extract application name from parent folder
  const workspaceDir = process.cwd(); // e.g., "c:/Users/AdityaSengupta/shopizer"
  const appName = path.basename(workspaceDir); // "shopizer"
  
  // Step 2.3: Filter buckets matching application name and sort by timestamp (latest first)
  const discoveryBuckets = buckets.filter(b =>
    b.name.startsWith(`${appName}-discovery-`)
  ).sort((a, b) => {
    // Extract timestamps: "shopizer-discovery-20260626-192000" → "20260626-192000"
    const timestampA = a.name.split('-discovery-')[1];
    const timestampB = b.name.split('-discovery-')[1];
    return timestampB.localeCompare(timestampA); // Descending order (latest first)
  });
  
  if (discoveryBuckets.length === 0) {
    throw new Error(`No discovery buckets found for application: ${appName}`);
  }
  
  const latestBucket = discoveryBuckets[0].name;
  console.log(`  📦 Using bucket: ${latestBucket}`);
  
  // Step 2.4: Discover the object prefix used in the discovery bucket
  // (The discovery agent may store files under a "discovery/" prefix)
  const allObjects = await mcpTool('use_mcp_tool', {
    server_name: 'minio',
    tool_name: 'list_objects',
    arguments: { bucketName: latestBucket, recursive: true }
  });
  // Detect prefix by finding where DISCOVERY_SUMMARY.md lives
  const summaryObj = allObjects.find(o => o.name.endsWith('DISCOVERY_SUMMARY.md'));
  const discoveryPrefix = summaryObj
    ? summaryObj.name.slice(0, summaryObj.name.indexOf('DISCOVERY_SUMMARY.md'))
    : ''; // empty string = files are at bucket root

  console.log(`  📂 Discovery prefix in bucket: "${discoveryPrefix || '(root)'}"`);

  // Step 2.5: Download all discovery documents using the resolved prefix
  const discoveryDocs = [
    'DISCOVERY_SUMMARY.md',
    'ARCHITECTURE_INVENTORY.md',
    'BUSINESS_RULES.md',
    'INTEGRATIONS.md',
    'DEPENDENCY_MAP.md',
    'DATABASE_INVENTORY.md',
    'DATABASE_SUMMARY.md'
  ];
  
  for (const doc of discoveryDocs) {
    await mcpTool('use_mcp_tool', {
      server_name: 'minio',
      tool_name: 'download_object',
      arguments: {
        bucketName: latestBucket,
        objectName: `${discoveryPrefix}${doc}`,
        filePath: `temp/discovery/${doc}`
      }
    });
    console.log(`  ✅ Downloaded ${doc}`);
  }
  
  // Step 2.4: Read downloaded documents
  evidence.minio = {
    discoverySummary: await readFile('temp/discovery/DISCOVERY_SUMMARY.md'),
    architectureInventory: await readFile('temp/discovery/ARCHITECTURE_INVENTORY.md'),
    businessRules: await readFile('temp/discovery/BUSINESS_RULES.md'),
    integrations: await readFile('temp/discovery/INTEGRATIONS.md'),
    dependencyMap: await readFile('temp/discovery/DEPENDENCY_MAP.md'),
    databaseInventory: await readFile('temp/discovery/DATABASE_INVENTORY.md'),
    databaseSummary: await readFile('temp/discovery/DATABASE_SUMMARY.md')
  };
  
  console.log(`  ✅ Loaded all discovery documents from MinIO`);
  
} catch (error) {
  console.warn(`  ⚠️  Could not retrieve from MinIO: ${error.message}`);
  console.log(`  📂 Falling back to local context/ directory`);
  
  // Fallback to local files
  evidence.minio = {
    discoverySummary: await readFile('context/DISCOVERY_SUMMARY.md'),
    architectureInventory: await readFile('context/ARCHITECTURE_INVENTORY.md'),
    businessRules: await readFile('context/BUSINESS_RULES.md'),
    integrations: await readFile('context/INTEGRATIONS.md'),
    dependencyMap: await readFile('context/DEPENDENCY_MAP.md'),
    databaseInventory: await readFile('context/DATABASE_INVENTORY.md'),
    databaseSummary: await readFile('context/DATABASE_SUMMARY.md')
  };
}

// Read additional local evidence sources
console.log(`📂 Scanning local evidence sources...`);

evidence.local = {
  sqlScripts: await readFiles(config.sqlFiles),
  boundedContext: boundedContext,
  sourceCode: await scanDirectory(config.sourceCode)
};

console.log(`  ✅ Found ${evidence.local.sqlScripts.length} SQL files`);
console.log(`  ✅ Scanned ${Object.keys(evidence.local.sourceCode).length} source directories`);
```

### Step 2.5: Enrich Evidence from Neo4j (per service)

**Purpose**: Query Neo4j for objective, code-derived facts that cannot come from
discovery documents. Run four targeted Cypher queries for each service and attach
the results to `service.graphEvidence` before spec-kit generation begins.

If Neo4j is unreachable, log a warning and set `service.graphEvidence = {}` so the
rest of the flow is unaffected.

```typescript
console.log(`\n🔬 Querying Neo4j for graph evidence (per service)...\n`);

for (const service of serviceList) {
  try {

    // ── Query A: Business rules on classes owned by this bounded context ──────
    // Used by: OpenAPI error responses, SQL CHECK constraints, spec.md rules list
    const classRulesResult = await neo4jReadCypher(`
      MATCH (bc:BoundedContext {name: $contextName})-[:OWNS_DATA]->(t:Table)
            <-[:WRITES_TO]-(c:Class)
      WHERE c.businessRules IS NOT NULL
      RETURN c.name            AS className,
             c.description     AS classDescription,
             c.businessRules   AS businessRules
      ORDER BY c.name
    `, { contextName: service.boundedContext });

    // ── Query B: Method signatures + descriptions for this context ────────────
    // Used by: OpenAPI operationId, summary, request/response body shapes
    const methodsResult = await neo4jReadCypher(`
      MATCH (bc:BoundedContext {name: $contextName})-[:OWNS_DATA]->(t:Table)
            <-[:WRITES_TO]-(c:Class)-[:CONTAINS]->(m:Method)
      WHERE m.signature IS NOT NULL AND m.description IS NOT NULL
      RETURN m.name         AS methodName,
             m.signature    AS signature,
             m.description  AS description,
             m.businessRule AS businessRule,
             c.name         AS className
      ORDER BY c.name, m.name
    `, { contextName: service.boundedContext });

    // ── Query C: Bounded context recommendation score ─────────────────────────
    // Used by: design doc migration phase ordering (EXCELLENT → first, CONSIDER → last)
    const bcResult = await neo4jReadCypher(`
      MATCH (bc:BoundedContext {name: $contextName})
      RETURN bc.name           AS name,
             bc.description    AS description,
             bc.recommendation AS recommendation
    `, { contextName: service.boundedContext });

    // ── Query D: Cross-context DEPENDS_ON edges ───────────────────────────────
    // Used by: design doc upstream/downstream sections, Saga pattern recommendation
    const depsResult = await neo4jReadCypher(`
      MATCH (c:Class)-[:DEPENDS_ON]->(c2:Class)
      WHERE c.package IS NOT NULL AND c2.package IS NOT NULL
        AND (
          c.package  CONTAINS toLower($contextName) OR
          c2.package CONTAINS toLower($contextName)
        )
      RETURN c.name      AS fromClass,
             c.package   AS fromPackage,
             c2.name     AS toClass,
             c2.package  AS toPackage
      ORDER BY c.name
    `, { contextName: service.boundedContext });

    service.graphEvidence = {
      classRules:     classRulesResult.records,   // [{className, classDescription, businessRules[]}]
      methods:        methodsResult.records,       // [{methodName, signature, description, businessRule, className}]
      boundedContext: bcResult.records[0] ?? null, // {name, description, recommendation}
      crossDeps:      depsResult.records           // [{fromClass, fromPackage, toClass, toPackage}]
    };

    const ruleCount   = service.graphEvidence.classRules.reduce((n, r) => n + (r.businessRules?.length ?? 0), 0);
    const methodCount = service.graphEvidence.methods.length;
    const rec         = service.graphEvidence.boundedContext?.recommendation ?? 'N/A';
    const depCount    = service.graphEvidence.crossDeps.length;

    console.log(`  ✅ ${service.name}: ${ruleCount} business rules, ${methodCount} methods, recommendation=${rec}, ${depCount} cross-deps`);

  } catch (err) {
    console.warn(`  ⚠️  Neo4j unavailable for ${service.name}: ${err.message} — continuing without graph evidence`);
    service.graphEvidence = { classRules: [], methods: [], boundedContext: null, crossDeps: [] };
  }
}

console.log(`\n✅ Neo4j graph evidence collected for all services`);
```

**How `graphEvidence` is used downstream:**

| Field | Used in |
|---|---|
| `classRules[].businessRules` | OpenAPI: `400`/`422` error scenarios per endpoint; SQL: `CHECK` constraint comments; `/speckit.specify` argument: `Business rules:` clause |
| `methods[].signature` + `.description` | OpenAPI: `operationId`, `summary`, parameter names derived from method signature; `/speckit.specify` argument: operation list |
| `boundedContext.recommendation` | Design doc §11 migration phase ordering; `CONSIDER` score adds an Open Question about boundary stability |
| `crossDeps` | Design doc §6.1/§6.2 upstream/downstream; Saga pattern recommended when `transferFunds`-style multi-account methods are detected |

### Step 3: Ensure Spec Kit Artifacts Exist (spec.md, plan.md, tasks.md)

**Purpose**: Ensure spec.md, plan.md, and tasks.md exist for every service before
generating design artifacts. These are produced by the `/speckit.specify`,
`/speckit.plan`, and `/speckit.tasks` Bob slash commands — **not** by any MCP tool.

**IMPORTANT**: Do NOT use the `spec-kit` MCP server tools (`speckit_specify`,
`speckit_plan`, `speckit_tasks`). The underlying `specify` CLI v0.9.4 does not
expose the subcommands those MCP tools call. They will always fail with
"path not found". Use the Bob slash commands instead, which are installed at
`.bob/commands/speckit.*.md` by `specify init --here --integration bob`.

**Pre-requisite check** — confirm the project is initialised:

```
# .specify/ directory must exist at the project root.
# If it does not:
specify init --here --no-git --integration bob --force
```

**For each service in the CSV, check whether its spec directory already exists.**
Spec-kit creates numbered directories under `specs/`:
- First service  → `specs/001-{service-name}/`
- Second service → `specs/002-{service-name}/`
- etc.

Scan `specs/` for a directory whose name ends with `-{service-name}` (kebab-case).

```
// Resolve the spec directory for a given service
function findSpecDir(serviceName) {
  const kebab = toKebabCase(serviceName);
  // e.g. scan specs/ for any dir matching /^\d{3,}-catalog-service$/
  return glob(`specs/*-${kebab}`)[0] ?? null;
}
```

**For each service, run the three slash commands in order if the artifact is missing:**

#### 3.1 — Generate spec.md via `/speckit.specify`

If `specs/*-{service-name}/spec.md` does not exist, invoke:

```
/speckit.specify {service-name}: {capability}. Owns tables: {tables}.
Aggregate root: {aggregate-root}.
Business rules: {graph-rules-if-any, else csv-rules}.
Operations: {graph-method-descriptions-if-any}.
External integrations: {external-systems}. Tech stack: Spring Boot 2.5,
PostgreSQL, Spring Data JPA. Upstream: {upstream}. Downstream: {downstream}.
Migration priority: {graph-recommendation-score}.
```

Compose the argument from the CSV row **enriched with `service.graphEvidence`**:
- `{graph-rules-if-any}` — join `service.graphEvidence.classRules[*].businessRules`
  into a comma-separated list; fall back to the CSV `Business Rules` column if empty.
- `{graph-method-descriptions-if-any}` — join up to 5 `service.graphEvidence.methods[*].description`
  values (semicolon-separated); omit the `Operations:` clause entirely if the array is empty.
- `{graph-recommendation-score}` — `service.graphEvidence.boundedContext?.recommendation`
  (e.g. `EXCELLENT`, `GOOD`, `CONSIDER`); omit the `Migration priority:` clause if null.

Compose the argument from the corresponding row in the microservices CSV.
The slash command will:
- Create `specs/{NNN}-{service-name}/` automatically (sequential numbering)
- Copy `.specify/templates/spec-template.md` as the starting point
- Fill the spec with user stories, functional requirements, success criteria,
  and assumptions derived from the description
- Validate against a quality checklist and write
  `specs/{NNN}-{service-name}/checklists/requirements.md`
- Persist the active feature path in `.specify/feature.json`

After the command completes, set `service.specDir` to the created path.

#### 3.2 — Generate plan.md via `/speckit.plan`

If `{service.specDir}/plan.md` does not exist, invoke:

```
/speckit.plan
```

The slash command reads `{service.specDir}/spec.md` (located via
`.specify/feature.json`) and generates:
- `{service.specDir}/plan.md`       — technical architecture
- `{service.specDir}/research.md`   — resolved unknowns
- `{service.specDir}/data-model.md` — entity model
- `{service.specDir}/contracts/`    — API interface contracts

#### 3.3 — Generate tasks.md via `/speckit.tasks`

If `{service.specDir}/tasks.md` does not exist, invoke:

```
/speckit.tasks
```

The slash command reads `{service.specDir}/spec.md` and
`{service.specDir}/plan.md` (via `.specify/feature.json`) and generates
`{service.specDir}/tasks.md` — a dependency-ordered, phase-structured
implementation checklist where every task follows the format:

```
- [ ] T001 [P] [US1] Description with exact file path
```

**Run all three commands for one service before moving to the next**,
so `.specify/feature.json` always points to the correct active feature directory.

After all three commands complete, load the artifacts:

```typescript
console.log(`\n📖 Loading Spec Kit artifacts for ${serviceList.length} microservices...\n`);

for (const service of serviceList) {
  const specDir = findSpecDir(service.name);

  if (!specDir) {
    throw new Error(
      `Spec Kit directory not found for ${service.name}. ` +
      `Run /speckit.specify, /speckit.plan, /speckit.tasks first.`
    );
  }

  const specMd   = await readFile(`${specDir}/spec.md`);
  const planMd   = await readFile(`${specDir}/plan.md`);
  const tasksMd  = await readFile(`${specDir}/tasks.md`);

  if (!specMd || !planMd || !tasksMd) {
```
